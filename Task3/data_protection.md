# Классификация данных и их защита

|**Данные**|**В чём необходимость защиты**|**Инструменты защиты**|
|-|-|-|
| Персональные данные пациента | Доступ должен быть только у пациента и администратора (для некоторых действий). <br> При физической краже или несанкционированном доступе нельзя допускать доступ злоумышленника к персональным данным, это приведет к нарушению законодательства и потере доверия со стороны клиентов. | При хранении - шифрование базы данных, можно будет настроить в CRM, например, с помощью AES-256. <br> При передаче - использовать защищенные протоколы, например, TLS 1.2+. |
| Медицинские данные пациента (диагнозы, результаты анализов и тд) | Доступ должен быть только у пациента и доктора на время приёма. Ограничить доступ можно с помощью временных ролей или специальных атрибутов. <br> Утечка медицинских данных приведет к потере доверия пользователей. | При хранении - используем шифрование отдельной директории, т.к. все данные хранятся в Active Directory. Через некоторое время сырые данные можно архивировать. <br> При передаче - использовать TLS 1.2+. |
| Журнал записи | В новой системе все персональные данные будут лежать в CRM, а журналы будут ссылаться на пациентов и докторов с использованием токенизации. В таком виде утечка журнала не будет критична. А вот при передаче изменений расписания нужна защита, чтобы предотвратить подмену или удаление данных. | При хранении - токенизация для данных пациентов и докторов <br> При передаче - использовать TLS 1.2+ |
| Платежные транзакции | Данные нужно хранить в зашифрованном виде, т.к. там могут быть конфиденциальные данные. Доступ нужен только бухгалтерии, причем можно предоставлять его в обезличенном виде, для учета скорее всего не нужны, скажем, ФИО пациентов и прочее. Когда данные обработаны для учета, можно их архивировать и сохранять в зашифрованных файлах. | При хранении - шифрование с AES-256, архивирование после использование в зашифрованный файл. <br> При передаче - использовать TLS 1.2+, некоторые данные можно обфусцировать |
| Данные о ТМЦ | Как и с журналами, утечка не повлечет нарушение закона или потерю доверия, но может быть полезна конкурентам, поэтому данные все же нужно дополнительно защищать. | При хранении - шифрование на уровне базы данных, достаточно отдельных колонок с чувствительной информацией. <br> При передаче - использовать TLS 1.2+ |

## Дополнительно

Во-первых, ограничение доступа на основе ролей можно сразу настроить в LDAP, а в новой архитектуре системы с этим поможет Keycloak.

Также полезно будет настроить автоматические инструменты вроде DLP для предотвращения утечки, однако это может потребовать экспертизы, которой сейчас нет в компании.
Можно воспользоваться внешними экспертами или компаниями, которые настроят систему для анализа файлового сервера, email-ов и тд. Возможно, стоит даже сразу вложиться
в более сложную систему (вроде BigID) для автоматической классификации данных и мониторинга. При масштабировании компании сложно будет отследить, что со всеми данными
работа идет правильным образом, поэтому инструмент мониторинга будет тут крайне полезен.
